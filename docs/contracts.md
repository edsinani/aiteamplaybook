# Contracts between components

A contract is any shape two components must agree on: an API route and its payload, a queue message, a set of field names one service emits and another reads, a generated manifest. Contracts are where parallel work breaks and where agents fail silently, because an agent working on one side cannot see the other.

## The pattern

Every contract has three things.

1. A file in the repo that states the contract in machine-readable form. Generated where possible, never hand-edited.
2. A test on the producing side that fails when the file no longer matches what the code emits.
3. A test on the consuming side that fails when the code reads something the file does not contain.

The pair of tests is the point. One test tells you the contract is stale. The other tells you a consumer is dead. Without both, a rename on either side just makes the consumer see a sparse input and skip, and nobody notices for weeks.

## Worked example, generalized

A Python extraction service emits field names into a JSON blob per document type. A .NET rules engine reads those names through alias lists. Nothing else connected the two sides; each rule's unit tests hand-wrote their own field names, so a rename on either side failed silently.

The fix was `contracts/extraction-field-manifest.json`, generated by a script in the Python service that lists every field name each flattener emits, per document type, with line-item indices normalized. Two tests guard it:

- `test_field_manifest.py` in the Python service fails when the checked-in file no longer matches what the flatteners emit (stale manifest).
- `RuleFieldContractTests.cs` in the .NET tests fails when any rule consumes a field name no flattener emits (dead rule), naming the rule, its aliases and the document type.

The `contracts/README.md` says how to regenerate and which tests guard it. That README is the whole documentation of the boundary.

## Where contracts live

`contracts/` at the repo root, one file per contract, plus a README listing each file, its generator command and its two guard tests. The system design section 4 links here.

## Rules for tasks

A task that changes a contract is never `[P]`. It runs first, alone, and is merged before any task that depends on it starts. The task template's `Contract:` line makes this visible in the tracker, and the reviewer checks that both guard tests changed in the same PR.

## What counts as a contract

If two of these are true, it is a contract and gets the treatment above:

- Two deployable units depend on it.
- Changing it needs a coordinated release.
- The failure mode of a mismatch is silent (skipped, defaulted, empty) rather than loud (exception, 400).

## What the agent is told

In `AGENTS.md`: "Before changing anything under `contracts/` or any DTO, queue message or field name that another service reads, stop and say so. Contract changes are their own task."
